48 of the 61 route handlers are migrated and passing their existing tests — 312 tests green from `npm test -- --grep routes`. The remaining 13 are 9 routes blocked on session handling and 4 file-upload routes I haven't started. The week deadline still looks reachable, but only if the upload routes can use buffering rather than streaming.

One question needs your answer before I can finish the 9 blocked routes: is renewal-on-read acceptable for the 30-minute idle logout? Those routes use `express-session` with a `connect-redis` v6 store, which is Express-only. I wrote a 40-line Redis adapter shim for `@fastify/session`, and it passes 3 of the 4 session tests. The failure is session-touch renewal semantics: the Fastify plugin renews a session when it's read, while Express renewed it when it's written, so under Fastify an idle user with a page polling in the background would never get logged out. If that's not acceptable, the fallback is keeping those 9 routes on Express behind a proxy until we swap the session store.

The 4 file-upload routes are the schedule risk. Replacing multer with `@fastify/multipart` is a real rewrite — roughly 3-4 hours — because the multipart streaming semantics differ, and I have to choose buffering or streaming. Buffering is about a day and fits the week; streaming is 2-3 days and probably doesn't.

Two pre-existing bugs surfaced while migrating, neither caused by the migration. `routes/admin/export.js` never awaits the CSV write, so large exports truncate silently; I reproduced it with an export over 10MB. `routes/webhooks/stripe.js` validates the Stripe webhook signature after parsing the JSON body, so a request that makes the parse throw skips signature validation. My best guess is that it's benign because the parse error path returns early, but I have not confirmed that, and it's a signature-validation path, so it's worth someone else's eyes.
